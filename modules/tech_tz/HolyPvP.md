# Техническое задание — модуль HolyPvP

> Документ описывает фактическую реализацию модуля на основе анализа исходного кода
> (`modules/HolyPvP`, ветка `mc-1.21.4`). Служит спецификацией для восстановления,
> доработки и поддержки плагина.

---

## 1. Общие сведения

| Параметр | Значение |
|---|---|
| Название плагина | HolyPvP |
| Артефакт (Maven) | `HolyPvP` (родитель `world.example:exampleworld-parent:1.0.0`) |
| Версия | 1.0 |
| Главный класс | `ru.nezxenka.holypvp.HolyPvP` |
| API-версия Bukkit | 1.16 |
| Автор (plugin.yml) | nezxenka |
| Команда | `/pvp` (алиас `/holypvp`) |
| Права | не объявлены (команда доступна всем) |

**Назначение:** кросс-серверный поиск PvP-соперников. Игрок через меню заявляет о
поиске боя одного из двух типов — «Поединок» (обычный, в основном мире) или
«Смертельная схватка» (в отдельном мире, с ареной, ограниченной world border, и
лутом проигравшего). Заявки игроков хранятся в общей MySQL-таблице, поэтому игроки
разных серверов сети видят заявки друг друга; сам бой возможен только между игроками
одного сервера. Побеждённый теряет ресурсы, победа анонсируется через LiteBans broadcast.

---

## 2. Требования к окружению и зависимости

### 2.1. Сервер
- Paper/Spigot, API 1.16 (проект собирается против paper-api 1.21.4 из родительского POM,
  Java 21 — `maven.compiler.release=21` в родителе).
- MySQL/MariaDB — обязательна, подключение создаётся при включении плагина.

### 2.2. Внешние плагины (используются через консольные команды, в plugin.yml не объявлены)
| Команда | Назначение |
|---|---|
| `updatepvp <игрок1> <игрок2>` / `updatepvp <игрок> 0` | синхронизация статуса PvP с внешним плагином (обновление при старте боя, каждые 15 с и по завершению) |
| `spawn <игрок> -s` | тихая телепортация на спавн (после схватки/при принудительной остановке) |
| `litebans broadcast <текст>` | объявление о поиске соперника и о победе |

### 2.3. Библиотеки
- jetbrains annotations 24.1.0 (provided). Прочее — Bukkit/Paper API (provided из родительского POM).

## 3. Архитектура (структура пакетов)

```
ru.nezxenka.holypvp
├── HolyPvP           — главный класс: регистрация слушателя и команды /pvp,
│                       инициализация DatabaseManager/ConfigManager, per-player WorldBorder,
│                       onDisable-очистка (удаление профилей своего сервера, stopForce всех боёв)
│   └── HolyPvP.PvpCommand (private static) — CommandExecutor+TabExecutor команды /pvp
├── Pvp               — одна пара бойцов: телепорт, обратный отсчёт, арена, задачи,
│                       обработка смерти/выхода, сообщения о завершении
├── PvpMenu           — меню «Поиск PvP» (выбор типа боя / отмена поиска)
├── PvpList           — меню «Доступные игры» (список заявок из БД + просмотр инвентаря)
├── PvpListener       — события: смерть, выход/кик, урон до старта боя, клики в трёх меню,
│                       контроль границ арены (Move/Teleport), join в мире схватки
├── PlayerProfile     — заявка игрока: ник, сервер, FightType, инвентарь (Base64), hash;
│                       сериализация Inventory ↔ Base64 (BukkitObjectStream, 41 слот)
│   └── PlayerProfile.FightType — enum DUEL / DEADLY_FIGHT
├── DatabaseManager   — прямое JDBC-подключение MySQL, CRUD таблицы player_profiles
└── ConfigManager     — отдельная загрузка config.yml, get/set имени сервера
```

## 4. Функциональные требования

### 4.1. Команда `/pvp` (алиас `/holypvp`)
| Форма | Поведение |
|---|---|
| `/pvp` (игрок) | если игрок уже в бою — сообщение `messages.deny.already`; иначе открыть меню «Поиск PvP» |
| `/pvp list` | открыть меню «Доступные игры» (список активных заявок) |
| `/pvp` (консоль) | сообщение «Только игроки могут использовать эту команду» (зашито в код) |
| TabComplete | единственный вариант — `list` |

### 4.2. Меню «Поиск PvP» (PvpMenu)
- Инвентарь 27 слотов, заголовок `Поиск PvP` + длинный хвост пробелов +
  маркер `[holypvp:pvp]` (идентификация меню по заголовку).
- Слот 18 — NETHER_STAR «Полезная информация» (статичный текст о правилах).
- Слот 11 — LIME_CONCRETE «Поиск поединка» (PDC-ключ `holypvp:update` = `pvp`) — только если у игрока **нет** заявки в БД.
- Слот 15 — PURPLE_CONCRETE «Поиск смертельной схватки» (`smert`) — только если нет заявки.
- Слот 13 — RED_CONCRETE «Покинуть сражение» (`cancel`) — только если заявка есть.
- Все клики отменяются; проверка наличия заявки — синхронное обращение к БД
  (`hasPlayerProfile(...).get()`).

**Требования к вступлению в поиск** (проверяется при клике по кнопке):
- не менее **15 золотых яблок** (GOLDEN_APPLE, сумма стеков) в инвентаре;
- «Поединок»: полный комплект брони — шлем (незеритовый/алмазный/золотой),
  нагрудник/штаны/ботинки (незеритовые или алмазные);
- «Смертельная схватка»: шлем (незеритовый или золотой), нагрудник/штаны/ботинки — только незеритовые.
- При несоответствии — сообщения с текстом требований (зашиты в код, цвета `&c`/`&f`/`&6`).
- При успехе: инвентарь закрывается, создаётся `PlayerProfile` (снимок инвентаря на момент заявки),
  в консоль отправляется `litebans broadcast <случайное сообщение из messages.searching.pvp|smertka>`
  с плейсхолдерами `%player%`, `%server%`.
- `cancel`: сообщение «Поиск поединка отменен», профиль удаляется из БД.

### 4.3. Меню «Доступные игры» (PvpList)
- Инвентарь 54 слота, заголовок `&0Доступные игры ... [holypvp:list]`.
- Рамка: синие стеклянные панели (слоты 0,1,2,6,7,8,45,46,47,51,52,53),
  оранжевые (3,4,5,48,49,50).
- Все профили из `player_profiles` — начиная со слота 9:
  - LIME_CONCRECE «Поединок с: <ник>» / лор «Поединок состоится на: <сервер>» (DUEL);
  - PURPLE_CONCRETE «Смертельная схватка с: <ник>» (DEADLY_FIGHT);
  - лор: «Левый клик — начать поединок», «Правый клик — инвентарь игрока»;
  - PDC-ключ `holypvp:name` = ник заявителя.
- **ЛКМ** по заявке: отказы — сам с собой (`messages.deny.self`), чужой сервер
  («перейдите на сервер: <имя>»), цель оффлайн/данные не загрузились; повторная проверка
  требований к инвентарю (по типу боя); при успехе — создаётся `Pvp`, оба игрока
  вносятся в `pvpHashMap`, цель получает «Соперник найден, ожидайте...».
- **ПКМ** — меню «Просмотр инвентаря ... [holypvp:invsee]» (54 слота): содержимое
  сохранённого в заявке инвентаря + ARROW «Назад» в слоте 53 (возврат в список).
  Если инвентарь заявки не десериализовался — сообщение об ошибке.

### 4.4. Ход боя (`Pvp`)
- При создании: профили обоих игроков удаляются из БД; `canPvp = false`.
- **Мир боя**: «Поединок» — мир из конфига (см. §9 об ошибке пути — фактически всегда `world`);
  «Смертельная схватка» — мир `deadly_fight` (создаётся через `WorldCreator`, если отсутствует).
- **Точка боя**: случайные координаты. Поединок: x, z ∈ [−900, 900]; схватка: x, z ∈ [−10000, 10000].
  Цикл перегенерации, пока биом точки не входит в список `settings.biomes.pvp|smertka`.
  Игрок 2 размещается со смещением ±10 блоков по x и z; оба смотрят друг на друга
  (направление по вектору между точками).
- **Схватка**: пер-игрокочный WorldBorder с центром в середине между игроками,
  радиус 50 (размер 100), warning distance 5, warning time 15; задача каждые 300 тиков (15 с)
  шлёт `updatepvp p1 p2`.
- **Отсчёт**: таймер с периодом 20 тиков, счётчик от 6; на каждом тике — Title `&e<N>`
  и звук ENTITY_EXPERIENCE_ORB_PICKUP обоим; при 0 — `canPvp = true`, звук ITEM_TOTEM_USE
  обоим, Title сбрасывается. До этого любой EntityDamageEvent участникам отменяется.
- **Границы арены** (только схватка; PlayerMoveEvent и PlayerTeleportEvent): при
  |dx| > 50 или |dz| > 50 от центра координата клампится к ±49.5, Y = highest block + 1
  (`event.setTo(...)`).
- **Смерть участника** (`PlayerDeathEvent`; также вызывается при выходе с сервера):
  - задачи отменяются, оба удаляются из `pvpHashMap`, world border снимается обоим,
    `updatepvp <ник> 0` обоим;
  - `litebans broadcast <случайная строка messages.finish>` с `%winner%`/`%looser%`;
  - только для схватки: победителю — сообщение `messages.left-time` и BossBar
    (BLUE, SOLID) «Победа! Вы покинете арену через N секунд.»; через 60 с (или при смене мира
    победителем) — `spawn <победитель> -s`, BossBar убирается.
- **Выход из арены победителем во время отсчёта телепортации** (`PlayerTeleportEvent`,
  смена мира): отменяет teleportTask либо вызывает `stopTp` — соперник получает
  «Вы были телепортированы на спавн...» и `spawn -s`.
- **Остановка плагина** (`stopForce` из onDisable): отмена задач, снятие border,
  `updatepvp ... 0`; для схватки — обоим `spawn <ник> -s`.
- **Join игрока в мире deadly_fight** (не в бою) — `spawn <ник>` (консоль).
- **Kick** участника: пара удаляется из карты, профиль кикнутого удаляется (бой не финализируется).

### 4.5. Права
В plugin.yml права не объявлены; проверки `hasPermission` в коде отсутствуют —
все функции доступны любому игроку.

## 6. Хранение данных

### 6.1. MySQL (обязательно), таблица `player_profiles`
Создаётся автоматически (`CREATE TABLE IF NOT EXISTS`):
```sql
player_profiles (
  nickname VARCHAR(16) PRIMARY KEY,
  server VARCHAR(32) NOT NULL,
  fight_type ENUM('DUEL', 'DEADLY_FIGHT') NOT NULL,
  inventory_base64 LONGBLOB NOT NULL,
  hash LONGBLOB NOT NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
```
- Подключение: одиночный `java.sql.Connection`, URL
  `jdbc:mysql://<host>/<db>?autoReconnect=true`; при обрыве переподключается лениво
  (`checkConnection`); все запросы — в `CompletableFuture` (ForkJoinPool, асинхронно).
- Инвентарь заявки: слоты 0–40 (36 ячеек + 4 брони + offhand) сериализуются
  `BukkitObjectOutputStream` + `Base64Coder` (snakeyaml) в `inventory_base64`;
  поле `hash` заполняется тем же значением (дубликат).
- Операции: create (INSERT), get (SELECT по нику), update, delete,
  getAll (полное чтение таблицы — используется менюом списка и onDisable).
- `onDisable`: удаляются все профили, у которых `server` совпадает с именем этого сервера,
  затем `stopForce` всех активных боёв.

## 7. Интеграции
- **LiteBans** — broadcast сообщений (консольная команда `litebans broadcast`).
- **Плагин команды `spawn`** — возврат на спавн (`spawn <ник> -s`).
- **Плагин команды `updatepvp`** — внешний учёт PvP-статуса.
- PlaceholderAPI/Vault — не используются.

---

## 8. Сценарий работы (основной поток)
1. Игрок `/pvp` → меню → клик «Поиск поединка/смертельной схватки» → проверка требований
   (15 золотых яблок + броня) → создание профиля в MySQL (снимок инвентаря).
2. Broadcast о поиске (litebans) с именем игрока и сервера.
3. Соперник на любом сервере сети: `/pvp` → `/pvp list` → видит заявку; ПКМ — просмотр
   инвентаря заявителя; ЛКМ — при условии «тот же сервер» и выполнения требований начинается бой.
4. Оба профиля удаляются, игроки телепортируются в случайную точку (схватка — отдельный мир,
   с per-player world border), 5-секундный отсчёт (урон заблокирован).
5. Бой; границы арены удерживаются Move/Teleport-обработчиками.
6. Смерть/выход проигравшего: broadcast победы, снятие border, `updatepvp ... 0`;
   в схватке победитель получает 60 секунд на сбор ресурсов (BossBar), затем `spawn -s`.
7. Перезаход в мир схватки вне боя — принудительный `spawn`.

## 9. Особенности реализации и известные ограничения
- **Ошибка пути конфига**: код читает `settings.settings.worlds.pvp|smertka`
  (двойной префикс `settings.settings`), которого в config.yml нет, — всегда используются
  default-значения `world` / `deadly_fight`. Смена миров через конфиг не работает.
- Блокирующее `CompletableFuture.get()` на главном потоке (PvpMenu, PvpList) —
  фризы при медленной БД.
- Формула прогресса BossBar `Math.max(Math.min((60-time)/60, 0.0), 1.0)` всегда даёт 1.0 —
  полоса не убывает (визуальный баг).
- В PvpList проверка `profile == null` выполняется после обращений к `profile.getNickname()` —
  потенциальный NPE при гонке (профиль удалён между чтением списка и кликом).
- `hash` в БД дублирует `inventory_base64`; INSERT без upsert — повторная вставка
  существующего ника падает с предупреждением (перед боем профили удаляются вручную).
- Кулдауны/состояние боёв — только в памяти (`HashMap<Player, Pvp>`); перезапуск
  прерывает бои через `stopForce`.
- Незащищённые ники: ключ таблицы — VARCHAR(16) (ник), не UUID.
- Поддержка HEX — только через `&x&r&g&b`-последовательности (`translateAlternateColorCodes`).
- Комментарий в коде `clearWorldBorder`: на 1.16.5 граница была пакетной и исчезала сама,
  в новой версии per-player API-граница снимается явно в путях завершения боя.
- Прав нет вовсе; никаких GUI-прав/админ-команд не предусмотрено.
