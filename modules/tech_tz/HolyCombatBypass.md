# Техническое задание — модуль HolyCombatBypass

> Документ описывает фактическую реализацию модуля на основе анализа исходного кода
> (`modules/HolyCombatBypass`, ветка `mc-1.21.4`). Служит спецификацией для восстановления,
> доработки и поддержки плагина.

---

## 1. Общие сведения

| Параметр | Значение |
|---|---|
| Название плагина | HolyCombatBypass |
| Артефакт (Maven) | `HolyCombatBypass` (родитель `world.example:exampleworld-parent:1.0.0`) |
| Версия | 1.0 |
| Главный класс | `ru.holydev.holycombatbypass.HolyCombatBypass` |
| API-версия Bukkit | 1.21 |
| Автор | HolyZako |
| Описание (plugin.yml) | «Lets staff use commands while in PvP, which AntiRelog otherwise blocks unconditionally» |

**Назначение:** одноцелевой «патч-плагин» для AntiRelog. AntiRelog блокирует
**все** команды игрока, находящегося в бою (PvP), и не предоставляет права-исключения
в своём обработчике команд. HolyCombatBypass слушает то же событие
(`PlayerCommandPreprocessEvent`) на приоритете HIGHEST — позже AntiRelog (NORMAL) —
и «расканилливает» событие, если у игрока есть право обхода. Сам AntiRelog при
этом не модифицируется (правка переживает его обновления).

---

## 2. Требования к окружению и зависимости

| Зависимость | Версия | Scope | Обязательность |
|---|---|---|---|
| AntiRelog | — | не зависит в Maven; `softdepend` в plugin.yml | мягкая (вся идея плагина — обойти его; без AntiRelog плагин безвреден, но бесполезен) |

- Зависимостей в pom нет. Сервер: Paper/Spigot API 1.21 (сборка Java 21).
- `softdepend: [AntiRelog]` гарантирует загрузку после AntiRelog (корректный
  порядок регистрации листенеров).

---

## 3. Архитектура

```
ru.holydev.holycombatbypass
└── HolyCombatBypass — JavaPlugin + Listener; один обработчик
    PlayerCommandPreprocessEvent (HIGHEST, ignoreCancelled = false):
    если событие отменено (AntiRelog'ом) и у игрока есть одно из прав
    BYPASS = {"holycombat.commands", "antirelog.bypass"} → setCancelled(false)
```

Рationale из javadoc класса: обработчик AntiRelog при блокировке смотрит только
на `disable-commands-in-pvp`, состояние PvP и белый список команд; право
`antirelog.bypass` проверяется у него лишь при **старте** боя, но не в обработчике
команд.

## 4. Функциональные требования

### 4.1. События
| Событие | Приоритет | ignoreCancelled | Поведение |
|---|---|---|---|
| `PlayerCommandPreprocessEvent` | `HIGHEST` | `false` | если событие НЕ отменено — выйти (ничего не делать); если отменено — при наличии любого права из `holycombat.commands` / `antirelog.bypass` снять отмену (`setCancelled(false)`) |

Т.е. плагин не создаёт собственных блокировок — только возвращает команду,
уже отменённую другим плагином (фактически AntiRelog, но формально — любым,
отменившим событие раньше, включая другие плагины приоритетов NORMAL/HIGH).

### 4.2. Права (permissions, объявлены в plugin.yml)
| Право | Default | Описание |
|---|---|---|
| `holycombat.commands` | op | «Разрешает вводить команды в режиме боя» |

Дополнительно в коде проверяется (не объявлено здесь, объявлено в AntiRelog):
| Право | Описание |
|---|---|
| `antirelog.bypass` | родное право AntiRelog — тоже снимает блокировку команд |

### 4.3. Команды
- Нет.

| Интеграция | Характер |
|---|---|
| AntiRelog | неявная, по событию: HolyCombatBypass должен выполняться ПОСЛЕ его обработчика (приоритет HIGHEST против NORMAL) и просто снимает cancel; никакие классы AntiRelog не используются |

---

## 8. Сценарий работы
1. Игрок входит в PvP → AntiRelog помечает его как «в бою».
2. Игрок (член стаффа) вводит команду, например `/tp`.
3. Обработчик AntiRelog (NORMAL) отменяет событие — команда заблокирована.
4. Обработчик HolyCombatBypass (HIGHEST) видит отменённое событие.
5. Проверяет права: `holycombat.commands` или `antirelog.bypass`.
6. Право есть → `setCancelled(false)` — команда выполняется сервером.
7. Права нет → отмена остаётся в силе (поведение AntiRelog не меняется).

---

## 9. Особенности реализации и известные ограничения
- Плугин снимает отмену с **любого** отменённого `PlayerCommandPreprocessEvent`,
  не только порождённого AntiRelog (если другой плагин отменит команду по иным
  причинам раньше HIGHEST, стакф это тоже обойдёт) — `ignoreCancelled=false` +
  отсутствие проверки источника.
- Если AntiRelog (или иной блокирующий плагин) перевесит свой обработчик на
  приоритет HIGHEST/MONSTER/выше или начнёт блокировать иначе (не через cancel
  события), обход перестанет работать молча.
- Право проверяется на каждый ввод команды — дополнительной нагрузки нет, но и
  кэширования нет.
- Метод `onEnable` пишет в лог «Enabled - staff can use commands during PvP».
